## Fuzzing Native iOS Libraries: Harnesses, Emulation & Coverage

Fuzzing native frameworks and dynamic libraries (`.dylib`, `.framework`, or Mach-O binaries in `dyld_shared_cache`) on iOS presents unique challenges due to closed-source constraints, code signing, non-standard IPC mechanisms, and ARM64-only execution environments.

This technical guide covers modern approaches to fuzzing native iOS binaries: from target extraction and harness creation to instrumentation techniques using **libFuzzer**, **AFL++**, **Frida**, and CPU emulation via **Unicorn Engine**.

---

## 1. Fuzzing Methodologies on iOS

Depending on source code availability and execution targets, three main approaches exist:

```
                  +-----------------------------------+
                  |  iOS Native Library Fuzzing       |
                  +-----------------+-----------------+
                                    |
     +------------------------------+------------------------------+
     |                              |                              |
[1. On-Device Native]       [2. Userland Emulation]        [3. Source-Level / macOS]
- Real iOS Environment      - High throughput (Linux/x86)  - macOS shared code
- Apple Silicon / Jailbreak - Unicorn / QEMU-user          - ASan / libFuzzer directly
- Statically Instrumented   - Frida-Stalker / QEMU-AFL    - Recompiled Xcode Targets
```

1. **macOS Equivalent / Cross-Platform Code (Highest Speed):** Many Apple userland framework binaries (e.g., ImageIO, CoreText, libarchive) share code between macOS and iOS. Compiling or running tests natively on macOS using ASan/libFuzzer provides high execution speed without iOS sandbox overhead.
2. **Emulated Execution (High Throughput / Scale):** Dumping the iOS shared cache or library binary and running it inside a headless emulator on x86 Linux (e.g., Unicorn or QEMU user mode with ARM64 support).
3. **On-Device / Corellium (Maximum Accuracy):** Executing the harness directly on an Apple Silicon device (jailbroken) or Corellium VM to maintain 100% native IPC/Mach dependency behavior.

## 2. Target Extraction: Processing `dyld_shared_cache`

On iOS, most native system libraries are unified into a single monolithic file called the `dyld_shared_cache`. Before fuzzing a library (e.g., `libxml2.dylib` or `CoreGraphics`), you must extract it.

### 2.1 Extracting dylibs using `dyld_shared_cache_util` or ipsw

```bash
# Using ipsw to extract a specific framework from dyld_shared_cache
ipsw dyld split dyld_shared_cache_arm64e -o ./extracted_libraries/

# Locate the target shared library
ls ./extracted_libraries/System/Library/Frameworks/ImageIO.framework/ImageIO
```

## 3. Building a Native C/C++ Harness

To fuzz a target library function (e.g., a custom parser or Apple decoder API), you must create a standalone executable (harness) that receives raw byte buffers from the fuzzer and passes them into the target entrypoint.

### 3.1 Reverse Engineering the Target Entrypoint

Assume reverse engineering reveals a parsing function inside a target binary:

```c
// Target Signature found in IDA/Ghidra
int ParsePayload(const uint8_t *data, size_t size, uint32_t flags);
```

### 3.2 Writing a libFuzzer Harness (`harness.cpp`)

```cpp
#include <stdint.h>
#include <stddef.h>
#include <dlfcn.h>
#include <stdio.h>

// Typedef matching target function
typedef int (*ParsePayload_t)(const uint8_t *data, size_t size, uint32_t flags);

static ParsePayload_t g_ParsePayload = NULL;

extern "C" int LLVMFuzzerInitialize(int *argc, char ***argv) {
    // Dynamically load target framework/dylib
    void *handle = dlopen("/System/Library/Frameworks/TargetFramework.framework/TargetFramework", RTLD_LAZY);
    if (!handle) {
        fprintf(stderr, "[-] Failed to load target library: %s\n", dlerror());
        return 0;
    }

    // Resolve unexported symbol via dlsym or offset
    g_ParsePayload = (ParsePayload_t)dlsym(handle, "ParsePayload");
    if (!g_ParsePayload) {
        fprintf(stderr, "[-] Symbol resolution failed\n");
        return 0;
    }

    return 0;
}

extern "C" int LLVMFuzzerTestOneInput(const uint8_t *Data, size_t Size) {
    if (Size < 4) return 0; // Filter non-viable inputs early

    // Execute target function with fuzzer data
    g_ParsePayload(Data, Size, 0);

    return 0;
}
```

## 4. Coverage-Guided Fuzzing without Source: Frida-Mode & AFL++

When fuzzing proprietary iOS binaries, source code is unavailable, preventing standard compiler instrumentation (`-fsanitize=fuzzer,address`).

Using **AFL++** paired with **Frida** mode provides coverage-guided dynamic instrumentation on ARM64 macOS or iOS targets.

### 4.1 Running AFL++ with Frida Instrumentation

```bash
# Compile harness targeting AFL++
clang -o fuzz_harness harness.cpp -ldl

# Run AFL++ with Frida-Mode (-O) for binary coverage tracing
afl-fuzz -i ./in_dir -o ./out_dir -O -- ./fuzz_harness @@
```

### 4.2 Configuring Frida Stalker for Targeted Coverage (`custom_script.js`)

To reduce overhead, filter coverage tracing to only the target library address space rather than system libraries:

```javascript
// Frida instrumentation script for AFL++
const targetModule = Module.load("/System/Library/Frameworks/TargetFramework.framework/TargetFramework");

Afl.print(`[+] Filtering Stalker coverage to: ${targetModule.name}`);

// Restrict coverage instrumentation to target binary bounds
Afl.setStalkerFilter({
    allowList: [targetModule.base, targetModule.base.add(targetModule.size)]
});
```

## 5. Detecting Vulnerabilities: ASan & Memory Sanitization

Finding memory corruption bugs in ARM64 iOS binaries requires precise memory tracking:

1. **AddressSanitizer (ASan):** On macOS cross-targets, compile with `-fsanitize=address`. ASan replaces allocator routines (`malloc`, `free`) with poison-zone padded wrappers to instantly detect out-of-bounds (OOB) reads/writes and use-after-free (UAF) vulnerabilities.
2. **libgmalloc (Guard Malloc):** On native iOS debug sessions, load `libgmalloc.dylib` to place every allocation on a distinct virtual page bounded by read/write guard pages:
   ```bash
   DYLD_INSERT_LIBRARIES=/usr/lib/libgmalloc.dylib ./fuzz_harness
   ```

## 7. Next Steps & Best Practices

1. **Minimize Harness Overhead:** Avoid repeatedly calling `dlopen()` or initializing heavy frameworks inside `LLVMFuzzerTestOneInput`. Move setup tasks inside `LLVMFuzzerInitialize`.
2. **Stub Out IPC Dependencies:** Replace Mach port messaging calls or IPC IPC stubs (`mach_msg`) with static mocks to prevent harness hangs or sandbox failures during fuzzing iterations.
3. **Corpus Minimization:** Use `afl-cmin` and `afl-tmin` to trim redundant inputs before launching multi-threaded fuzzing campaigns.
